## 1. 手动测试用例

通用前置流程（每次测试都走这套）：

1. 在 aardio IDE 中打开项目根目录的 `main.aardio`，按 **F5** 启动主窗口。
2. 点「加载文件」或「加载文件夹」载入待测文件。
3. 左侧「添加规则」配置改名规则；预览区（`lvPreview`）会**自动刷新**，六列分别为：
   `原名称 / 目标名称 / 状态 / 说明或错误 / 原始完整路径 / 目标完整路径`。
4. 点「执行重命名」→ 确认弹窗 → 结果弹窗。
5. 需要回退时点「撤销上一次操作」。

### 1.1 普通改名测试

- 步骤：载入若干普通文件（`photo.jpg` 等）→ 添加「添加字符：前缀 `IMG_`」→ 预览目标为 `IMG_photo.jpg` → 执行 → 确认。
- 预期：全部成功；磁盘文件名变为 `IMG_*`；状态栏提示「执行成功…可撤销」；点「撤销上一次操作」后文件名还原。
- 通过标准：磁盘名与预览完全一致；撤销后完全还原。

### 1.2 链式改名测试

- 场景：`a→b`、`b→c`、`c→d`（顺序位移，非互换）。
- 构造：准备 `a.txt / b.txt / c.txt`，用「文本替换 / 正则」把名字整体改写（如 `a→b`、`b→c`、`c→d`）。
- 预期：`precheck` 把这类标为 **warning**（目标被本批次其它待处理文件占用，链式）；`validate` 仍放行（两阶段执行正是为它设计）；执行后全部到位。
- 通过标准：最终 `a→b / b→c / c→d` 正确；磁盘**无 `~$rename_*` 临时名残留**。

### 1.3 循环改名测试（两两互换）

- 场景：`a→b`、`b→a`。
- 预期：`precheck/validate` 标记风险（目标被批次占用）；两阶段计划经临时名中转，应能把 `a`、`b` 互换成功。
- 通过标准：执行后 `a`、`b` 名字互换；**不丢文件、不出现「目标已被占用」失败**；磁盘无 `~$rename_*` 残留；撤销可还原。

### 1.4 大批量文件测试

- 步骤：在临时目录生成 **5000+** 个文件 → 「加载文件夹」→ 添加规则 → 预览 → 点执行。
- 预期：UI **不卡死**（执行在后台线程，窗口仍可拖动，状态栏显示「正在执行重命名，请稍候…」）；预览在合理时间返回；执行在后台完成；弹窗显示成功数量。
- 通过标准：所有文件改名成功且无遗漏；执行过程中窗口可正常交互。

### 1.5 执行失败测试

- 制造失败：加载文件后，手动在磁盘上**删除其中一个待改名文件**（或把某个目标路径预先占用 / 锁定），再执行。
- 预期：执行中途失败 → 自动回滚已执行步骤（`executor.rollback`）→ 弹窗提示「失败步骤 / 已自动恢复：是 / 否」；磁盘回到执行前状态（无半成品、无残留临时名）。
- 通过标准：失败**未造成文件丢失或残留**；若回滚成功，则「不可撤销」（见 §4 设计保障，避免二次撤销误删）。
- 另测（前置拦截）：目标被**批次之外**的文件占用 → `precheck/validate` 直接判 `error`，执行前拦截，**完全不碰磁盘**。

### 1.6 Undo 测试

- 步骤：成功执行一次 → 点「撤销上一次操作」→ 确认。
- 预期：文件按逆序改回原名；状态栏提示；再次点撤销应提示「无可撤销」（同一批次不重复撤销）。
- 通过标准：磁盘名完全还原；重复撤销不出错、不删文件。

## 3. 兼容性与稳定性检查

### 3.1 DPI 缩放

- 代码现状：`mainForm.applyLayout` 已按 `dpiX / dpiY` 把设计像素换算成实际像素，
  listview 列宽也按同一 `dpiScale` 同步，避免高 DPI 下列被挤出可视区。
- 验证：在 **100% / 125% / 150% / 175%** 缩放下分别启动，检查：
  - 控件无重叠、无溢出、文字不被截断；
  - 预览列表六列完整可见（尤其「状态」列）；
  - 窗口最大化 / 还原后布局正常。
- 预期：布局正常。若 aardio 未声明 DPI 感知，系统会位图缩放整窗（可用但略糊），功能不受影响——记录实际表现。

### 3.2 窗口大小变化

- 代码现状：`winform.onSize → applyLayout` 重排；`win.ui.minmax(winform, 860, 560)` 限制最小客户区，防止压坏布局。
- 验证：拖动改变窗口大小（含拖到很小、最大化、还原）；检查左列规则列表填满剩余高度、右侧预览区随宽伸缩、按钮不重叠。
- 预期：任意尺寸下无控件重叠 / 出界。

### 3.3 长文件名

- 代码现状：`precheck.invalidNameReason` 仅校验非法字符 / 保留名 / 尾空格与尾点，
  **未校验文件名字节长度，也未启用 `\\?\` 长路径前缀**。Windows 默认 `MAX_PATH=260`（含目录）；
  Win10+ 若开启长路径策略或 API 长路径感知可突破。
- 风险：超长文件名或深层目录可能执行失败（`move` 失败），但 `executor` 会失败即回滚，**不会丢文件**。
- 验证：构造文件名接近 / 超过 255 字符、以及目录层级很深（路径接近 260）的样例，执行改名，记录结果。
- 预期 / 处置：若失败应安全回滚；建议后续在 `precheck` 增加长度提示（**非本次改动**）。

### 3.4 中文文件名

- 代码现状：aardio 字符串为 Unicode；`nameutil.charCount` 用 `string.len` 计数（汉字计 1）；
  regex 预设含「中文字符」范围（`[\x{4e00}-\x{9fa5}]+`）。
- 验证：加载含中文名的文件（`报告.txt`、`照片.png`），加前缀 / 替换 / 正则（中文字符）规则，预览与执行。
- 预期：改名正确，无乱码，磁盘名与预览一致。

### 3.5 Emoji 文件名

- 代码现状：aardio 字符串内部 UTF-16，`string.len` 对代理对（一个 emoji）计为 2 个「字符」；
  `nameutil` 的 `midChars / tailChars / charIndexOf` 按此计数，按「字符位置」的规则
  （前 N 个 / 后 N 个 / 指定位置 / 首字母大写 / 序列位置等）可能把 emoji 算成 2 格，导致位置偏移。
- 风险：规则计算结果可能与直觉不符（显示与执行本身通常没问题）。
- 验证：文件名含 📷 / 😀 等，应用「前缀」「后 N 个字符」规则，检查目标名是否符合预期；执行改名确认文件名可正常写入。
- 预期：执行安全；位置类规则结果需人工确认是否符合预期，必要时记录为已知限制。

## 4. 已知风险汇总

1. **长文件名 / 超深目录**：无 260 限制防护与长路径前缀 → 可能执行失败（已保证安全回滚，不丢文件）。
2. **Emoji 等代理对字符**：按字符规则计数偏差 → 位置类规则结果可能偏移。
3. **性能数据**：为实测项，本文档未填（见 §2），需运行 `perfTest.aardio` 后补录。
4. **DPI 表现**：取决于 aardio 是否声明 DPI 感知，需实机确认外观清晰度。
5. **设计已保障（非风险）**：`history.undoableResult` 在「失败且已成功回滚」时返回 `false`，
   使该会话不可撤销，避免对已被回滚的文件二次撤销导致误删——失败场景下的撤销是安全的。
